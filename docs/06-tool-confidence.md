# Tool confidence: a draft argument for using Zyn in a safety-related project

Date: 13 November 2026.
Status: **draft, author-made, not reviewed by a functional safety engineer.** It sets out how a project could classify Zyn under ISO 26262-8:2018 clause 11 ("Confidence in the use of software tools"), and what evidence Zyn can give. It is not a qualification, a certificate, or a claim of compliance. The project using Zyn owns the classification and must check it against the standard itself.

## 1. How clause 11 works, in short

A project analyses each **use case** of a tool:

- **Tool impact (TI).** TI1: there is no possibility that a malfunction of the tool introduces an error into the product or fails to detect one. TI2: all other cases.
- **Tool error detection (TD).** How confident the project is that a malfunction, and the wrong output it causes, is prevented or detected (by the tool itself or by later process steps). TD1 high, TD2 medium, TD3 everything else.
- **Tool confidence level (TCL).** TI1 gives TCL1. TI2 with TD1 gives TCL1, with TD2 gives TCL2, with TD3 gives TCL3.
- **TCL1 needs no qualification.** TCL2 and TCL3 need qualification by one or more of: increased confidence from use, evaluation of the tool development process, validation of the software tool, or development in accordance with a safety standard; which methods are recommended depends on the ASIL.

The classification belongs to the use case, not the tool. The same Zyn function can be TCL1 in one project and TCL2 in another.

## 2. Zyn's design choices that bear on TD

| Measure | What it does | Where |
|---|---|---|
| Human decision on every item | Only a named person approves or rejects; the database refuses decisions without a name | `harness/audit/store.py` |
| Quote verification | Every extracted requirement and AI finding must quote source text; code confirms the quote is in the source | `harness/sift/checks.py`, `harness/outside.py` |
| Values from source only | Numbers not in the source are flagged; clarifications use `<TBD>` placeholders, never invented values | `harness/sift/checks.py` |
| Code checks before generation | Anvil specs are checked against the requirement text and the DBC; failing specs cannot be approved | `harness/anvil/validate.py` |
| Deterministic generation | Test cases are generated by code from approved specs, not written by a model | `harness/anvil/generate.py` |
| Fault-kill score | Generated cases are run against a correct simulation and injected faults; a case failing on the correct simulation marks the spec or generator wrong | `harness/anvil/simulate.py`, `score.py` |
| Formal set check | Specs written as formal statements and checked for contradictions | `harness/anvil/formal.py` |
| Run-to-run stability | AI review can be repeated; findings show how many passes reported them | `harness/sift/check.py` |
| Append-only audit log, hash chain | Every prompt, response and decision is kept; the evidence export hashes events in a chain | `harness/audit/store.py`, `harness/evidence.py` |
| Five verdicts | Model or infrastructure failure is "broken", never mistaken for a pass or a finding | `harness/evidence.py` |

## 3. Use cases and a proposed classification

Each row is a starting point for the project's own analysis.

| ID | Use case | TI | TD argument | Proposed TCL |
|---|---|---|---|---|
| U1 | Sift extracts requirements from a specification; a person approves each one against its quoted source | TI2: a wrong or missing requirement could reach the product | Each requirement shows its verbatim quote and page; code flags ungrounded quotes, changed modal verbs and new values; a person reviews every item. **Omissions** are the weak point: a requirement the model never extracted has nothing to review. Mitigation: coverage review of the source by the person, Sift Delta on later revisions | TD2, so **TCL2**, unless the project adds an independent completeness review of the source (then a TD1 argument may be made) |
| U2 | Sift Review flags quality problems in a requirement set as an aid to a human review that happens anyway | TI1 if the human review does not rely on Zyn to find problems (Zyn only adds findings); TI2 if the project drops or shortens its own review because of Zyn | Findings are advice; missing findings do not remove the human review | **TCL1** while the human review is unchanged; reassess if it is reduced |
| U3 | Anvil generates test cases from approved requirements, used to verify the product | TI2: a wrong test could pass a faulty product | Specs checked against requirement text and DBC; a person approves each spec; generation is deterministic code; every case is run against a correct simulation (must pass) and injected faults (fault-kill score); assumed values are listed per case. Faults outside the fault list and errors in the simulation itself are not caught by these measures | TD2, so **TCL2**; qualification by validation of the software tool (the test suite, the fault model) is the natural method |
| U4 | Anvil Review and checker mode review tests or requirements produced by other tools | TI1 if used only as an extra check on top of the project's own review | Findings are advice | **TCL1** |
| U5 | Evidence report and audit chain support an assessment | TI2 if the record is the only evidence of review | Hash chain detects later changes; the report is generated from the append-only log; JUnit and HTML can be cross-checked against the log | TD1 for record integrity is arguable; the project decides |

## 4. Evidence Zyn can give for qualification (TCL2)

For "validation of the software tool":

1. **Automated test suite**: `pytest` over the harness (169 tests at the time of writing), run offline with no model.
2. **Public-data evaluations**: QuRE, PROMISE and RTEMS results with the method and caveats ([04-public-evals.md](04-public-evals.md)), and the versioned benchmark pack (`python -m harness pack`).
3. **Fault model and fault-kill results** for generated tests, per template.
4. **Known limitations**, listed in the README and in each evidence report.
5. **Version identification**: git commit of the tool, prompt file names (never edited in place), model profile and served model recorded with every answer.

For "increased confidence from use": the audit log already records every use, decision and override; `python -m harness metrics` and the calibration table summarise them.

## 5. Open points before any real use

- A functional safety engineer reviews this classification for the project's use cases and ASIL.
- The model behind each AI step is outside the project's control. The tool's measures (quotes, code checks, human decisions) are what carries the argument, not the model's accuracy. Model changes should be re-benchmarked with the pack before use.
- The simulation used for the fault-kill score is built from the specs themselves; it cannot detect a spec that misreads the requirement in a self-consistent way. The formal set check and human approval are the measures for that.
- ISO/PAS 8800 (AI in road vehicles) and the EU AI Act may add expectations for the AI components; not covered here.
- DO-330 (aerospace tool qualification) follows a different scheme and is not covered.
